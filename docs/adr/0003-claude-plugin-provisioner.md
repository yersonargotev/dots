# Drive Claude Code plugins through the provisioner allowlist

The Provisioner contract (ADR 0001, `internal/provision`) versions a tool invocation — the tool plus a declarative flag spec — and renders it into an exact, idempotent command, never the intellectual layer the tool regenerates. Until now `gentle-ai` was the only allowlisted tool. A fresh machine still lost the user's Claude Code plugin setup (e.g. `chrome-devtools-mcp`), because that state lives in `~/.claude.json` and `~/.claude/plugins/` — machine state with absolute paths and per-project history that must not enter the Source of Truth. We will add `claude` as a second allowlisted provisioner tool and model each plugin concern as its own provisioner entry: one entry renders `claude plugin marketplace add <source>`, a second renders `claude plugin install <plugin>@<from> --scope user`. Manifest order guarantees the marketplace is registered before the plugin installs. The `chrome-devtools-mcp` plugin was originally added under the `desktop` profile because it drives Google Chrome, a desktop GUI prerequisite; ADR 0008 later moved it to `web` because the user-facing capability is browser/frontend tooling.

This passes the opinionated-tool litmus test (`docs/scope.md`): reproducing a daily-used plugin on the author's own machines in one command is exactly the guarded-bootstrap value the scope protects, not speculative generality. It does not turn `dots` into a generic command runner — the allowlist stays closed (`gentle-ai`, `claude`) and each tool renders through a fixed, validated set of subcommands.

**Considered Options**: A bootstrap shell script (`claude mcp add` / `claude plugin install`) was rejected because it moves risky logic out of testable Go and bypasses the Install Plan, doctor readiness, dependency checks, and the HOME-threaded sandbox — the exact guarantees ADR 0001 centralises. Folding the plugin install into the existing `gentle-ai` provisioner was rejected because gentle-ai owns the persona/skills/agents layer under `~/.claude`, not the user's third-party plugin choices — wrong layer, no overlap. Modelling a plugin as a single provisioner that emits both the marketplace-add and the install was rejected because the Provisioner abstraction is one-entry/one-command (pure `RenderCommand`, single-arg `Step`/`Readiness`/`RunItem`); two entries keep that invariant and make ordering explicit. A plain MCP-server entry (`claude mcp add chrome-devtools npx chrome-devtools-mcp@latest`) was deferred: it is simpler but drops the skills the plugin bundles, and modelling the plain-MCP shape is unbuilt until a real need appears.

**Consequences**: `ProvisionerSpec` now carries two dialects — gentle-ai install flags and the Claude `marketplace`/`plugin`/`from` fields — kept disjoint by validation (a claude spec rejects gentle-ai flags and vice versa; a claude spec must set exactly one of `marketplace` or `plugin`, and `from` is required with and exclusive to `plugin`). Idempotency is a load-bearing property and was verified against `claude` 2.1.179 for both rendered commands: re-running `claude plugin marketplace add <source>` ("already on disk") and `claude plugin install <plugin>@<from> --scope user` ("already installed") both exit 0 without overwriting, so the provisioner is safe on every `dots install`. `claude` is declared as a manual dependency (no package mapping); if it is absent the provisioner is reported not-ready and skipped, never auto-installed. The plain-MCP provisioner shape and any non-`chrome-devtools` plugins remain deferred until needed.

**Claude settings ownership**: `~/.claude/settings.json` is co-owned. dots owns the portable baseline in `configs/claude/settings.json` (model, theme, editor mode, environment flags, status line, and allowed tools), while Claude, gentle-ai, and plugin tooling may add runtime or tool-managed keys under the same JSON file. The manifest therefore marks that entry with `ownership: json-subset` instead of treating the copy as whole-file owned. `dots status` and `dots doctor` compare the source as a required JSON subset after Installation Metadata proves dots installed the target: extra object keys and array elements are expected, but changed or missing dots-owned values remain Drift. Without matching Installation Metadata, a pre-existing superset remains a Conflict rather than being silently adopted.

**Superseding profile note**: ADR 0008 keeps this provisioning mechanism but moves Chrome DevTools selection from `desktop` to the explicit `web` profile so browser/frontend tooling stays opt-in.
