# Integrate dependency provisioning into install with provider fallback

`dots install <profile>` should provision the required Dependencies for the selected Profile before applying Managed Configuration, so a fresh machine can converge with one command instead of requiring a separate `dots deps install` step. This partially supersedes ADR 0001's v1 boundary that kept automatic package installation outside the install flow: the project now accepts guarded dependency execution as part of the primary install contract because configuration that cannot run is not a successful install.

The dependency planner will choose from ordered providers rather than a single OS tier. On Linux, distro package managers such as `apt` remain valid for base packages, and Homebrew fallback is opt-in per Dependency through `linux_homebrew` so only reviewed CLI/runtime tools use Linuxbrew when it is already installed. GUI apps, fonts, and tools without validated Linuxbrew support stay manual instead of rendering false installability. `dots` will not install Homebrew itself; if a selected required Dependency opts into Homebrew and Homebrew is absent, install must stop with clear setup guidance.

Dependencies are classified as required or optional. Required Dependencies gate installation: if they are missing, unavailable, or fail to install, `dots install` aborts before touching Managed Configuration. Optional Dependencies are reported but do not block configuration. An explicit `--skip-deps` escape hatch may bypass dependency provisioning for recovery, development, or manually managed machines.

The `core` Tag now represents the Core Development Baseline: a general development environment, not a minimal shell setup. Core includes shell and terminal foundations plus common development runtimes and package tools. Runtime ownership is tool-specific: Node is installed as LTS through `fnm`, Rust through `rustup`, Go through Homebrew, `uv` is installed without provisioning a global Python, and `uv`/`pnpm`/`bun` can use reviewed user-local providers before Linuxbrew fallback when explicit manifest policy is present. The `pnpm` provider uses pinned standalone `@pnpm/linux-*` executable artifacts rather than Corepack shims or global sudo-backed npm installation.

**Considered Options**: Keeping `dots deps install` separate was rejected because it preserves the broken fresh-machine experience where configs install but required tools are missing. Using only the distro package manager on Linux was rejected because Ubuntu/Debian package availability for tools such as Starship, Zellij, Atuin, and eza varies by suite and can make the plan lie about installability. Installing Homebrew automatically was rejected because bootstrapping a package manager mutates PATH and system state beyond the boundary `dots` should own.

**Consequences**: The dependency model must learn provider fallback, provider presence checks, and required/optional semantics. Install plans should surface dependency actions before file actions and provisioners. Tests must verify that install aborts before filesystem changes when required Dependencies cannot be satisfied, and that `--skip-deps` preserves the old config-only behavior intentionally.
