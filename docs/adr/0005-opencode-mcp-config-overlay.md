# Give OpenCode the chrome-devtools MCP server through a merged config overlay

The author wants the `chrome-devtools` MCP server on OpenCode too, to match Claude (ADR 0003) and Codex (ADR 0004). OpenCode is the awkward case: it exposes no plugin/MCP install CLI that mutates one fragment (unlike `claude plugin install` or `codex mcp add`), and its global `~/.config/opencode/opencode.json` is co-owned — `gentle-ai` renders the agent/orchestrator layer into it, so dots must not version or overwrite that file (the existing seed test guards exactly this). Versioning the whole `opencode.json` as a Managed Entry would clobber gentle-ai's output and, because file Entries install before the gentle-ai provisioner runs, lose the race anyway.

OpenCode does, however, merge several config sources rather than replacing them. The `OPENCODE_CONFIG` environment variable names a custom config file that is combined with the global `opencode.json`. So dots owns a small overlay fragment (`configs/opencode/mcp.json`) that declares only the `chrome-devtools` MCP server, installs it to `~/.config/opencode-dots.json` (outside gentle-ai's config directory), and points `OPENCODE_CONFIG` at it from the managed `zshenv`. OpenCode merges the overlay over gentle-ai's rendered config; neither owner touches the other's file.

This passes the opinionated-tool litmus test: it reproduces a daily-used MCP server on a fresh machine using mechanisms dots already has — a file Entry plus a guarded shell export — without inventing a JSON-merge engine or a new install strategy.

**Considered Options**: A whole-file Managed Entry on `~/.config/opencode/opencode.json` was rejected: the file is co-owned by gentle-ai and dots would clobber it (and lose the install-order race). `opencode mcp add` was rejected because it mutates that same gentle-ai-owned global file rather than a dots-owned fragment — the overlay keeps the two domains disjoint, which the CLI cannot. Deferring OpenCode entirely (as ADR 0004 first proposed) was rejected once the merge behavior was verified, because the overlay is a clean, low-cost path. Authoring a JSON deep-merge install strategy in dots was rejected as speculative generality for a single key.

**Consequences**: The merge-not-replace behavior of `OPENCODE_CONFIG` is load-bearing and was verified against the installed OpenCode (`opencode debug config`): pointing `OPENCODE_CONFIG` at the fragment resolves `chrome-devtools` alongside the user's existing servers (`codegraph`, `context7`, `engram`) with the command and `environment` intact, and the full gentle-ai config is preserved. The overlay lives at `~/.config/opencode-dots.json`, deliberately outside `~/.config/opencode/` so it never appears in gentle-ai's git repository there. The `zshenv` export is guarded on the file's existence, so a profile without the desktop fragment (the overlay is `desktop`-tagged) simply skips it. The prior invariant — dots must not version gentle-ai's rendered `opencode.json` — is refined, not dropped: the seed test now forbids `configs/opencode/opencode.json` specifically, while allowing the hand-authored overlay fragment. `OPENCODE_CONFIG` is a single-slot variable; if the author later needs it for another purpose this overlay must be reconciled with that use.
