# Expose a stable machine-readable output contract for agents

The Dotfiles CLI is increasingly driven by autonomous coding agents, not only humans at a terminal. Today every command renders through a dedicated `render_*.go` layer into human prose (`renderStatus`, `renderDoctor`, `renderDeps`), and `cmd/dots/main.go` collapses every outcome into two exit codes: `0` when `Execute` returns no error, `1` otherwise. An agent therefore cannot tell aligned Dotfiles Status from Drift without regex over text that the Golden Output Test is free to reformat, and `dots status` returns `0` whether the workstation matches the Source of Truth or has drifted. We will make the CLI agent-consumable by adding a single Agent Output Contract: a global `--output text|json` flag, one centralized JSON envelope rendered from the existing domain reports, and a semantic exit-code scheme that distinguishes a clean run, a divergent-but-healthy run, and an execution error. The contract is additive — `text` stays the default so human output and existing Golden Output Tests are unchanged.

The architecture already supports this at low cost. The domain layer (`internal/status`, `internal/plan`, `internal/doctor`) returns pure data structs (`status.Report`/`Entry`, `plan.Plan`/`Action`, `doctor.Report`/`SecretFinding`) with no presentation logic, and all output is written through `cmd.OutOrStdout()` rather than `os.Stdout`. The `domain → render` seam is exactly where a machine surface belongs: we add `json:` tags to those reports, add one `renderJSON` helper beside the existing text renderers, and branch on the persistent flag. We do not invent a second compute path. Non-interactive execution is already covered by Confirmed Install (`--yes`) and Text Prompt Mode (`--no-tui`); the contract only adds the rule that Machine Output Mode (`--output json`) implies non-interactive and must never emit a prompt onto the JSON stream.

**Agent Output Contract**: One JSON envelope shape for every command, versioned independently of the CLI binary so field changes are a reviewable break, not an accident. The envelope carries a `schema_version`, the `command` name, a `status` discriminator (`ok` | `findings` | `error`), and a `data` object whose shape is the command's domain report. Diagnostic data (Dotfiles Status entries, Install Plan actions, doctor checks, Dependency findings) is rendered from the same domain structs the text renderer consumes, so the two surfaces never disagree on the state they both report. Errors in Machine Output Mode are emitted as a structured `error` envelope on stdout — never a half-written human string — so an agent always receives parseable output regardless of outcome.

**JSON surface scope**: Every result-producing command under the persistent `--output json` flag emits an envelope on stdout. This includes informational commands (`version`, `manifest validate`), read-only diagnostics (`status`, `plan`, `doctor`, `deps check`, `deps plan`), previews (`install --dry-run`, `uninstall --dry-run`, `backups list`, `backups restore --dry-run`, `deps install --dry-run`, `update --dry-run`), and confirmed action commands. Human-only surfaces such as help text, shell completion scripts, and parent commands without a selected subcommand are rejected with an error envelope rather than emitting prose on stdout. The envelope carries the machine-meaningful report, not every sentence the text surface prints. Machine-local and advisory fields stay out of the contract — `plan`'s `resolved_source` (an absolute path that differs per machine and would break idempotent comparison), `deps`'s `probe_detail`/`hint` (truncated, unstable human prose), and restore's internal preserved-file paths are excluded; agents key on the portable and structured fields (`source`, `present`, `warning`, target paths, actions, and the `deps plan` install action). The error envelope is best-effort: a malformed invocation that fails before its command resolves (an unknown command, or a flag error parsed before `--output`) still reports on stderr with exit `1`, because no command context exists yet to label a JSON envelope.

**Semantic exit codes**: `0` means the command ran and the workstation is aligned (no Drift, no Conflict, no missing Dependency, no doctor concern), or an action command completed successfully. `2` means a read-only diagnostic command ran successfully but found a non-error divergence the caller should act on — Drift, an unresolved Conflict, a missing Dependency, or a doctor concern. `1` stays reserved for an execution error (bad manifest, I/O failure, misuse), so existing `|| handle-error` scripts still catch real failures and never confuse them with "ran fine, state diverges." Action commands keep `0`/`1`; the `2` findings code applies only where findings are the command result. The code is threaded through a single sentinel error type that `main.go` inspects with `errors.As`, so commands stay declarative and the exit-code policy lives in one place.

**Considered Options**: Per-command ad-hoc JSON (each command marshals its own shape) was rejected because it produces divergent field names and envelopes across `status`, `doctor`, and `deps`, which is worse than no JSON — an agent trusts the structure and breaks silently when one command drifts from the others. A separate `dots agent` subtree mirroring each read-only command was rejected because it forks the compute path and doubles the Golden Output Test surface for the same data. Keeping binary exit codes and asking agents to parse a summary line was rejected because it makes branching depend on prose that the renderer is explicitly allowed to change. Emitting JSON to stderr while keeping text on stdout was rejected because it prevents simple `dots status --output json | jq` pipelines and muddies the stream contract; instead, `--output json` owns stdout and diagnostics go to stderr.

**Consequences**: `dots status`, `dots plan`, `dots doctor`, and `dots deps` change their exit code from a constant `0` to `0`/`2` based on findings. This is a deliberate behavior change: any caller (including CI) that runs `dots status` and asserts exit `0` while Drift exists must move that assertion to the `text`/`2` contract or read the JSON envelope. Because the project is pre-1.0, the break is acceptable and is the entire point of the code. The domain reports (`status.Report`, `plan.Plan`, `doctor.Report`, and their nested types) gain `json:` tags, making their field names part of the public Agent Output Contract; renaming, removing, or changing the meaning of an existing field is now a `schema_version` bump caught by the JSON Golden Output Test (`TestEnvelopeGolden`), which locks the full envelope shape for every command. Adding a portable, optional field is schema-compatible and keeps the current `schema_version`, but still must update the matching JSON golden so agent-visible additions are reviewed deliberately. Schema version `3` permits selected action-command `error` envelopes to include a partial `data` report when the command already computed useful structured context before failing, such as dependency gate results plus the Install Plan. The persistent `--output` flag lives on the root command, so it is uniformly available and documented once. Because availability implies support for machine output, commands must either emit the envelope or reject invalid, non-interactive, or human-only misuse with an error envelope. `--instructions` self-description and a non-interactive `--on-conflict` selector are explicitly deferred: they are additive on top of this contract and unbuilt until a concrete agent workflow needs them. The contract does not turn `dots` into a generic data API — it exposes only the reports the CLI already computes, in a stable shape, for the read-only and action commands that already exist.
