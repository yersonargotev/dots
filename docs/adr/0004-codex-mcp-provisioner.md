# Drive the Codex chrome-devtools MCP server through the provisioner allowlist

The author runs the `chrome-devtools` MCP server in Claude Code (ADR 0003), Codex, and OpenCode, and wants a fresh machine to reproduce it everywhere. Codex, unlike Claude, ships no plugin marketplace for `chrome-devtools`: the `ChromeDevTools/chrome-devtools-mcp` repo provides a *Claude* plugin marketplace plus a generic MCP server, and Codex integrates that server with `codex mcp add chrome-devtools -- npx -y chrome-devtools-mcp@latest`. So the cross-agent primitive that achieves parity is the MCP server, not the plugin system. We add `codex` as a third allowlisted provisioner tool and model the MCP-server concern as a Provisioner Spec dialect (`mcp` + `command` + `env`) that renders one idempotent `codex mcp add` invocation. This realises the "plain MCP-server shape" ADR 0003 explicitly deferred until a real need appeared — the need has now appeared.

This passes the opinionated-tool litmus test (`docs/scope.md`): reproducing a daily-used MCP server on the author's own machines in one command is the guarded-bootstrap value the scope protects. The allowlist stays closed (`gentle-ai`, `claude`, `codex`) and each tool renders through a fixed, validated set of subcommands.

**Considered Options**: Mirroring the Claude plugin shape (`codex plugin marketplace add` / `codex plugin add`) was rejected because no Codex marketplace exists for `chrome-devtools`; the only working integration is `codex mcp add`. Versioning `~/.codex/config.toml` as a Managed Entry was rejected because that file is mixed machine state — absolute per-project paths, TUI state, and values adjacent to `auth.json` — the same anti-pattern ADR 0003 rejected for `~/.claude.json`; the Provisioner exists precisely so dots drives the one fragment it owns (`[mcp_servers.chrome-devtools]`) without versioning the whole file. Authoring a custom Codex marketplace that bundles the MCP server plus skills was rejected because it would put dots in the business of versioning the intellectual layer (Regenerated Content) the provisioner contract refuses to own, and because the skills layer is already owned by `gentle-ai` (its provisioner installs `codex`, `claude-code`, and `opencode` agents). Reusing the Claude `marketplace`/`plugin`/`from` fields was rejected as semantically false: there is no marketplace in this path.

**Consequences**: `ProvisionerSpec` now carries three mutually-exclusive dialects — gentle-ai install flags, the Claude `marketplace`/`plugin`/`from` fields, and the codex `mcp`/`command`/`env` fields — kept disjoint by validation (a codex spec rejects gentle-ai and claude fields; it must set `mcp` and a non-empty `command`). `env` is rendered as repeated `--env KEY=VALUE` flags in sorted-key order so the command stays deterministic, and it captures the author's portable, non-secret preferences (disabling update checks and usage statistics) so a fresh machine reproduces them. Idempotency is load-bearing and was verified against `codex` 0.140.0 in a temporary `CODEX_HOME`: `codex mcp add chrome-devtools -- npx -y chrome-devtools-mcp@latest` run twice exits 0 and leaves a single `[mcp_servers.chrome-devtools]` entry. `codex` is declared as a manual dependency (no package mapping); if it is absent the provisioner is reported not-ready and skipped, never auto-installed. Skills parity remains `gentle-ai`'s responsibility, not dots'. OpenCode parity is a separate concern with its own decision: OpenCode exposes no fragment-level MCP install CLI and its `opencode.json` is co-owned by gentle-ai, so it is handled as a merged config overlay rather than a Provisioner — see [`docs/adr/0005-opencode-mcp-config-overlay.md`](0005-opencode-mcp-config-overlay.md).

**Superseding profile note**: ADR 0008 keeps this provisioning mechanism but moves Chrome DevTools selection from `desktop` to the explicit `web` profile so browser/frontend tooling stays opt-in.
