# Split skill ownership between repo-managed skills and a skills.sh provisioner

Install Profiles reproduce the agent skills needed on a fresh machine without turning `dots` into a generic shell runner. The current Provisioner contract already gives us the right seam: `dots` versions a declarative tool invocation, renders one exact command, and keeps the allowlist closed. We keep that seam and use a hybrid ownership model. First-party or critical skills that the repository must audit and control belong in the Source of Truth as repository-managed configuration. Third-party skills belong behind the first-class `skills` provisioner that drives the `skills.sh` CLI declaratively. Existing `gentle-ai` skill support remains valid for the gentle-ai-owned agent/persona layer; it is not replaced by this decision.

This decision keeps the distinction sharp: `dots` decides *what the workstation role needs* through Profiles and tags, but it does not become a marketplace, package manager, or arbitrary command executor. The `skills` provisioner accepts reviewed package references, such as `owner/skill`, validates them, and renders a fixed `skills.sh` install command through a pinned npm CLI package. The provisioner is selected like any other Provisioner through tags and OS filters, appears in Install Plans and doctor/status output, and runs with the install's threaded `HOME` so sandbox validation never touches the operator's real home.

**Considered Options**: Versioning every skill directly in this repository was rejected for third-party skills because it vendors external intellectual content, creates update burden, and hides upstream provenance. It remains the right choice for first-party or critical skills because Git review gives the strongest reproducibility, auditability, and offline behavior. Using unpinned `npx skills add ...` as a raw shell command was rejected because arbitrary command hooks violate the Source of Truth and safety model: `dots` must stay an opinionated Dotfiles CLI with allowlisted Provisioners, not a task runner. Reimplementing `skills.sh` inside `dots` was rejected because it duplicates package-manager behavior and shifts maintenance away from the tool that owns skill discovery and install mechanics. Relying only on `gentle-ai spec.skills` was rejected as incomplete: gentle-ai owns its generated agent/persona/skills layer, while third-party skills from the broader skills ecosystem need their own explicit ownership boundary.

**Consequences**: The Install Manifest has a fourth allowlisted Provisioner tool, `skills`, with its own mutually-exclusive Provisioner Spec dialect for external skill packages. Validation rejects mixing that dialect with the existing `gentle-ai`, `claude`, or `codex` fields. Rendering stays deterministic and one-entry/one-command. Readiness declares the required executable(s) without auto-installing unsafe dependencies, and install/update execution reuses the existing HOME-threaded runner. Documentation explains the ownership split: repo-owned skills are Source of Truth; external `skills.sh` packages are Regenerated Content restored by re-running the provisioner; gentle-ai-managed skills remain owned by gentle-ai. Implementation is tracked in [#137](https://github.com/yersonargotev/dots/issues/137).
